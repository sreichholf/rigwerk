Model

  • Output stays the master stage: master level + mute, after Post EQ.
  • Below it: the output devices. Exactly one is the clock device. The chain (plugins, gate, EQ) runs on its callback.
  • Every other device follows: own ring, resampler, drift loop, cushion. It plays the finished mix.
  • RigWerk Out is a follower too, with an endpoint instead of a device picker. It can't be the clock device.

Live vs. restart

  • LIVE add/remove follower, level, mute, cushion, publish on/off.
  • RESTARTS BRIDGE clock device swap, clock device's device/rate/buffer.
  • Clock device missing → bridge can't start (as today). Follower missing → bridge runs without it; row stays in the session.

Windows publish

  • v1: RigWerk renders into an installed cable (VB-Cable). Row says Publish → VB-Cable; apps pick CABLE Output. The cable is greyed in the add list while Publish uses it.
  • v2: with the RigWerk Virtual driver it becomes RigWerk Out, renameable.
  • Neither present: the Virtual entry is greyed with the reason; Live shows "Not publishing".

Concept review questions

  • Enum: Output stays the master; add OutputDevice(n) like Plugin(n), plus an add state.
  • Clock model: one clock device + N followers, yes. Name it by clock, not "Listen": monitors are listened to too. PipeWire duplex: followers in the same graph need no ring. ASIO: one driver, so followers are WASAPI.
  • Overload: the chain runs once on the clock device; if it can't keep up, every follower runs dry together and shows it in its health.
  • Sessions: keep today's single output as the clock device; add an optional followers list so old presets load unchanged.

Out of scope here

  • Channel mapping per device lives on Signal Routing (next round): a device picker above the matrix.
  • Feed point per device (pre/post master): later, with routing.
  • Windows: one ASIO driver per process, so followers are WASAPI (or channels on the open ASIO driver, via Routing).
